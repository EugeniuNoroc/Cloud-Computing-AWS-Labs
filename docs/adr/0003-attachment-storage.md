# ADR-0003. Хранение вложений пользователей в Amazon S3

**Статус:** принято
**Дата:** 2026-11-04

## Контекст

В ЛР2 и ЛР3 вложения капсул (картинки и PDF) хранились в папке `storage/uploads` на корневом диске EBS сервера `timecapsule-dev-app`. Приложение само читало файл с диска и отдавало его браузеру.

Пока сервер один, это работает, но:
- файлы пользователей существуют только на одном диске: при пересоздании или потере сервера они пропадают (в ЛР3 их пришлось переносить вместе с образом AMI);
- нельзя запустить второй сервер приложения: у него не будет файлов первого;
- каждое скачивание проходит через PHP-FPM и занимает ресурсы маленького t3.micro.

Ограничения: учебный проект, минимальные расходы, регион eu-north-1, ключи доступа AWS не должны храниться на сервере и в публичном репозитории.

## Решение

Вложения хранятся в бакете **`timecapsule-dev-uploads-eugeniu-noroc`** под префиксом `uploads/`:

- бакет закрыт: Block Public Access, ACL отключены, политика бакета запрещает любые запросы без HTTPS;
- включено версионирование и правило жизненного цикла `timecapsule-dev-noncurrent`;
- приложение работает с S3 через AWS SDK от имени роли **`timecapsule-dev-app-role`**, привязанной к app-server. Политика `timecapsule-dev-app-s3` разрешает только `GetObject`, `PutObject`, `DeleteObject` на `uploads/*`;
- браузер получает файл по **подписанному URL** сроком 5 минут, который выдаёт приложение после проверки прав пользователя.

## Рассмотренные альтернативы

**1. Диск EBS сервера приложения (как в ЛР2–ЛР3).**
Проще всего: никаких новых сервисов и прав. Отклонён: файлы привязаны к одному серверу в одной зоне доступности, при Terminate диск удаляется вместе с ними, второй сервер их не видит. Масштабировать приложение горизонтально невозможно, а резервное копирование нужно настраивать отдельно (снимки EBS).

**2. Общая файловая система Amazon EFS.**
EFS монтируется по NFS сразу к нескольким серверам, в том числе в разных зонах, поэтому код приложения почти не меняется — файлы по-прежнему «лежат в папке». Отклонён: EFS заметно дороже S3 за гигабайт, требует mount targets в подсетях и правил Security Group для NFS (порт 2049), а скачивание по-прежнему идёт через сервер приложения. Версионирования объектов и подписанных ссылок в EFS нет.

**3. Объектное хранилище Amazon S3 (выбран).**
Не зависит от серверов и зон, хранит данные с высокой надёжностью, дешевле всего за гигабайт, умеет версионирование, жизненный цикл и подписанные URL. Минус: приложение пришлось переписать — модуль `src/storage.php` работает через AWS SDK, а не с файловой системой.

## Последствия

**Как пользователь получает файл и что ограничивает срок ссылки.**
Браузер обращается к приложению (`/capsules/{id}/file`). Приложение проверяет, что пользователь имеет право видеть капсулу и что она открыта, затем подписывает URL учётными данными роли и отвечает редиректом 302. Браузер скачивает файл напрямую из S3, минуя сервер. Срок ссылки ограничен параметром `X-Amz-Expires=300` (5 минут), который входит в подпись: изменить его или ключ объекта нельзя, S3 вернёт `SignatureDoesNotMatch`. После срока S3 отвечает `Request has expired`. Кроме того, ссылка не может пережить временные учётные данные роли, которыми подписана.

**Что защищает от случайного удаления и ограничивает рост стоимости.**
Версионирование: удаление капсулы создаёт только маркер удаления, предыдущая версия остаётся и может быть восстановлена. Политика приложения не содержит `s3:DeleteObjectVersion`, поэтому даже при утечке учётных данных роли нельзя стереть историю версий. Рост стоимости ограничивает правило `timecapsule-dev-noncurrent`: неактуальные версии через 30 дней переходят в более дешёвый класс Standard-IA, через 90 дней удаляются (кроме двух самых новых), незавершённые загрузки частями удаляются через 7 дней.

**Несколько серверов и балансировщик нагрузки.**
Сервер приложения теперь не хранит данных пользователей (stateless): на нём только код и настройки, база — на db-server, файлы — в S3. Поэтому можно запустить несколько серверов приложения в разных зонах доступности за балансировщиком: все они получат одну и ту же роль и будут работать с одним бакетом. Заменить сервер можно без переноса данных. Elastic IP при этом станет не нужен, пользователи будут обращаться к балансировщику. Остаётся одна зависимость от конкретного сервера — сессии в `storage/sessions`; их нужно будет перенести в общее хранилище (базу или кэш) или включить «липкие» сессии на балансировщике.

**Хуже / риски:**
- приложение зависит от S3 и AWS SDK: при недоступности S3 вложения не загружаются и не открываются;
- пересланную подписанную ссылку в течение 5 минут может открыть кто угодно; её нельзя отозвать досрочно, только дождаться истечения срока;
- маленькие файлы (меньше 128 КБ) не переходят в Standard-IA, поэтому экономия от правила жизненного цикла начнётся только на больших вложениях.
